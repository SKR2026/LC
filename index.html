Section 02

Scope of the Developer Panel

The Developer Panel is a purpose-built, covert administrative interface embedded within the Application. It exists solely to facilitate development, testing, quality assurance, and post-deployment maintenance activities. The following technical architecture defines its scope:

2.1 Identity & Session Architecture

The DMA is assigned a hardcoded internal identity: id __dev__, name Developer, email dev@polyplastics.internal, role admin, dept Engineering. These values are compiled into the Application source and never persisted to Firebase, localStorage, or any users array.

The DMA carries an internal flag _isDev: true, which activates a violet DEV badge (⚙ DEV) in the application navigation bar. This badge is visible only during active DMA sessions and is intentionally invisible to all Client users.

The bypass login check executes before any Firebase query. If the submitted credentials match the embedded DMA email and password (case-insensitive email comparison), authentication succeeds immediately without contacting Firestore or Firebase Auth, and the session lands on the full Admin view.

The DMA session is filtered out of all user listings within the application's Users panel via the exclusion predicate u.id !== '__dev__', ensuring the Developer identity is never visible to the Client in any user management screen.

2.2 Scope Boundary

The Developer Panel is scoped exclusively to the Administration view of the Application. On successful DMA login, the session is unconditionally routed to page = 'admin', granting all capabilities of the Admin Dashboard.

The Developer Panel does not include a separate visual interface, dedicated settings page, or additional UI components distinct from the standard Admin Dashboard — its distinction lies solely in the authentication mechanism, the _isDev flag, and the DEV badge indicator.

Section 06

Restrictions & Prohibited Conduct

No Unauthorised Production Access. The Developer shall not use the DMA to access the Production Environment for any purpose other than contracted support, maintenance, or emergency recovery. Accessing the Production Environment to view, extract, or copy Client compliance data for any purpose outside the scope of the engagement is strictly prohibited.

No Deletion of Live Data. The Developer shall not delete, truncate, or irreversibly modify any requirements, users, plants, or evidence files in the Production Firestore database without prior written authorisation from an authorised representative of the Client.

No Credential Disclosure. The DMA credentials (email address, password), Firebase API configuration, and any EmailJS or Azure AD credentials must not be disclosed, published, or transmitted to any person or system not explicitly authorised under this Provision. Credential storage in plain-text, source control repositories (e.g. public GitHub), or unsecured communication channels is prohibited.

No Persistence Beyond Engagement. The Developer must not retain working knowledge of, or access to, the production DMA credentials after the termination of any support or maintenance period. Post-engagement, credentials must be considered invalidated by the Client.

No Impersonation. The Developer must not use the DMA to impersonate Client users, create fake compliance entries, manipulate audit trails, or perform any action that could mislead the Client organisation regarding its actual compliance status.

No Email Misuse. The Developer must not use the integrated email capabilities (EmailJS / Microsoft Graph) to send unsolicited, unauthorised, or test emails to real Client personnel from the Production Environment without explicit Client approval. All email testing must be performed in a staging or development deployment.

No Competitive Use. The Developer may not use insights gained from DMA access to the Application — including its data architecture, business logic, compliance category structure, or escalation workflows — to develop or enhance competing products without prior written consent from the Client.

No Modification Without Agreement. The Developer must not modify the Application's source code, Firebase Security Rules, or connected service configurations in the Production Environment without a signed change request or support ticket issued by the Client.

⚠ Critical Prohibition — Source Code Exposure

Because the DMA credentials are hardcoded in the Application's source code (.html file), the entire source file must be treated as a Confidential Credential document. Committing this file to any public version control repository, sharing it via unencrypted channels, or hosting it on publicly-accessible static file servers without access controls constitutes a critical security breach under this Provision and must be reported immediately.

Section 07

Credential Handoff Obligations

The following mandatory protocol applies at the point of Application delivery to the Client:

Mandatory Pre-Delivery Password Rotation. Before delivering the final Application file to the Client, the Developer must replace the default DMA password dev@legal#2026!master with a new, secure, randomly-generated password of no fewer than 16 characters, comprising uppercase letters, lowercase letters, digits, and special characters. The Application source code comment reading // ← change before handoff serves as the explicit reminder of this obligation.

Credential Delivery Mechanism. The new DMA credentials (email and rotated password) shall be delivered to the Client's designated IT administrator or system owner through a separate, secure channel — such as encrypted email (PGP), a secured password manager share, or an in-person handover. They must not be included in the same delivery package as the Application file, documentation, or any publicly-accessible medium.

Credential Acknowledgement Receipt. The Client's authorised representative shall provide a written (or digitally signed) acknowledgement confirming receipt of the DMA credentials. This receipt forms part of the handoff documentation and must be retained by both parties.

Client's Post-Delivery Right to Rotate. The Client reserves the absolute right to rotate the DMA password at any time after delivery, without notice to the Developer, particularly: (a) upon expiry of the support/warranty period; (b) upon suspicion of credential compromise; (c) upon termination of the Developer's engagement; or (d) as part of any periodic security review.

Developer's Obligation upon Client-Side Rotation. If the Client rotates the DMA password, the Developer's access to the DMA is immediately and automatically terminated. The Developer must not attempt to recover, bypass, or reconstruct access without the Client's explicit, written authorisation and a new credential issuance.

Notification of Suspected Compromise. Either party who suspects the DMA credentials have been compromised, discovered by an unauthorised party, or exposed in any manner must notify the other party within 24 hours of discovery. The Client must immediately rotate the DMA password. The Developer must provide any information reasonably necessary to assess the scope of the compromise.

Section 08

Data Governance & Security

8.1 Data Ownership

All compliance data — requirements, user records, plant records, evidence files, audit history, and configuration — created in or imported into the Application belongs exclusively to the Client (Polyplastics India Ltd.). The Developer acquires no ownership, licence, or right to this data by virtue of DMA access.

Compliance data stored in Firebase Firestore and Firebase Storage is subject to Google's Firebase Terms of Service and privacy policy in addition to this Provision. The Client is responsible for ensuring their Firebase project complies with applicable Indian data protection laws including the Digital Personal Data Protection Act, 2023 (DPDPA).

8.2 Storage Architecture & Persistence

The Application uses a dual-persistence model: data is synchronised between Firebase Firestore (primary, cross-device) and browser localStorage (offline fallback). The DMA session does not create any Firebase Auth record and leaves no server-side trace of the developer identity in Firestore.

Admin settings including email credentials (EmailJS keys, Azure AD IDs) are stored solely in the user's browser localStorage under the key adminSettings. These are not encrypted at rest. The Client must ensure that the device used for Admin Settings configuration is secured and access-controlled.

The DMA session state is held exclusively in React component memory (useState) and does not persist across browser sessions. Closing or refreshing the browser terminates the DMA session without residue.

8.3 Security Obligations of the Developer

The Developer shall implement reasonable technical and organisational security measures to protect DMA credentials during the development and support period, including but not limited to: secure storage of credentials (password manager or encrypted vault), two-factor authentication on development workstations, and access limitation to Authorised Developer Personnel only.

The Developer must not use the same DMA password across multiple client deployments. Each delivery of the Application must have a unique, client-specific DMA password.

Section 13

Termination & Revocation of Developer Access

Automatic Termination Events. Developer access via the DMA shall automatically terminate, without notice, upon: (a) expiry of any contracted support or maintenance period; (b) the Client rotating the DMA password; (c) mutual agreement of the parties in writing; or (d) dissolution or insolvency of either party.

Client's Right to Immediate Revocation. The Client may immediately revoke DMA access at any time, for any reason, by rotating the DMA password. No compensation, notice period, or justification is required for such revocation. Revocation does not affect any outstanding payment obligations under the principal development contract.

Effect of Termination. Upon termination of Developer access: (a) the Developer must destroy all copies of the DMA credentials; (b) the Developer must cease all access to the Production Environment; (c) any data extracted from the Application during the engagement must be destroyed unless required by law; (d) the Client must confirm the DMA password has been rotated.

Survival. The following provisions survive termination of this Provision: § 6 (Restrictions), § 8.1 (Data Ownership), § 11 (Liability), § 12 (IP Ownership), and § 15 (Governing Law).
